# fcs_ok field-data verdict (backlog B1, closed)

**Question:** does the LoRa chip ever deliver a frame with a broken FCS? Martin's claim during
the 2026-08-21 wire audit: no — the chip drops bad frames itself, and the firmware's FCS
handling is unused/possibly broken. The full M2 gate (reject trailer-less/truncated frames)
was declined on that basis; instead, schema v24 stores per-frame `fcs_ok` on BLE data frames
(NULL for UDP/MH rows by design) so the claim could be tested against field data.

## Snapshots

| Date                        | NULL  | fcs_ok=1 | fcs_ok=0 |
| --------------------------- | ----- | -------- | -------- |
| 2026-08-21 21:45 (creation) | 18593 | 8        | 0        |
| 2026-09-05 (closing check)  | 20580 | 1550     | 0        |

Non-NULL rows grew from 8 to 1,550 with zero `fcs_ok=0` observed at any point.

## Decision

Claim confirmed. Closed 2026-09-05 — 1,550 BLE data frames is judged a sufficient sample
(the original due date, 2026-09-20, was not reached; Martin judged the sample size decisive
ahead of the date). M2's trailer-less/truncated-footer gate stays declined; the `fcs_ok`
column remains in schema (harmless, and keeps the option open if a future firmware or radio
ever produces a genuine mismatch).

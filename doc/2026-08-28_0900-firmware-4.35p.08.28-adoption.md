# Firmware v4.35p.08.28 adoption — BLE `I` regression, MHeard `SRC`/`GW`/`PP`

**Date:** 2026-08-28
**Firmware:** DK5EN fork `66aed467`, on upstream `dev` `fc83554e` (PRs #1102/#1103 merged)
**Node:** DK5EN-98, paired to mcapp.local
**Firmware-side issue reports:** `docs/issue-ble-i-register-mtu-20260828.md`,
`docs/issue-mh-json-size-budget-20260828.md` in the firmware tree

Three things reached the BLE wire on 2026-08-27: `FWDATE` on the `I` register, `SRC`/`GW`/`PP` on
the MHeard register, and a `serializeJson` buffer-size fix. One of them broke production. This
records what we found, what we changed, and the two decisions that were judgement calls.

---

## 1. The regression, and why it is ours to survive

Upstream `82db3d41` changed `I.FWDATE` from the integer `FLASH_VERSION` to
`__DATE__ " " __TIME__` — 14 chars more. That pushed the `I` document past the firmware's own frame
clamp in `addBLEComToOutBuffer()`: 245 bytes, minus the `0x44` type byte, so **244 usable chars of
JSON**. The firmware cuts mid-value, so what arrives is not a shortened object but an unparseable
one — the app loses every field, not just the last.

Field evidence, mcapp.local:

| Observation | Value                                                                |
| ----------- | -------------------------------------------------------------------- |
| First drop  | `2026-08-27 22:29:36` — the moment the node came up on the new build |
| Last drop   | `2026-08-28 07:50:53`                                                |
| Count       | 55, one per 10-minute reconciler cycle                               |
| Frame       | `247 bytes, 244 chars decoded`, `JSONDecodeError … column 242`       |

The 244 is the direct fingerprint of the clamp. Consequences while it lasted: `cached_ble_registers`
permanently missing `'I'`, `_detect_node_identity` never firing (so pairing-drift protection was
dead), the webapp's Identity card on placeholders, and the reconciler logging the identical
unactionable warning every 10 minutes for over nine hours — with the actual cause visible only in a
_different_ systemd unit's journal.

Upstream fixed it the next morning (`ba6eaefb`, `FWDATE` back to the integer). Verified in the
field: node reconnected 08:01:40, zero drops since, reconciler clean.

**But the overflow is still reachable.** The `GCB0..GCB5` array change (firmware issue §5.5) was
deliberately deferred to an app-coordinated PR, so a node with all six group-call slots populated
still exceeds the clamp by ~13 chars — and that case predates `FWDATE` entirely. It was simply
rarer. So the proxy has to survive a truncated register regardless of what the firmware does.

### What we changed

`ble_service/src/main.py` now salvages a truncated `D{` frame instead of dropping it: trim to the
end of the last **complete** top-level member, close the object, re-parse. Whole members only — a
value cut mid-string, mid-number or mid-escape is discarded with its member, never coerced or
defaulted. The existing "never apply half a value" rule is preserved exactly; what changed is that a
frame which loses only its tail is no longer thrown away whole.

`src/mcapp/main.py` de-spams the reconciler's steady-cadence warning: a new or changed missing set
still warns immediately, an unchanged one drops to DEBUG, and after one hour it emits exactly one
escalation that names the likely cause and points at `journalctl -u mcapp-ble.service`. The
reconciler still never gives up — that part was right.

## 2. MHeard: `SRC`, `GW`, `PP`

### Decision 1 — attribution is additive, not a rekey

`CALL` is the **last hop**: the station whose transmission this frame's `RSSI`/`SNR` actually
measured. `SRC` is the **originator**. Upstream measured that on a typical site roughly two thirds
of HEY observations are relayed, so `SRC != CALL` is the common case.

Two coherent options existed:

- **(a) Consistency** — set `src = SRC`, `via = CALL`, matching the UDP path and migration v22's
  model exactly. Uniform, one rule. But it stops writing a direct-link row for a neighbour that only
  ever relays other people's beacons: that reading moves onto the originator's row.
- **(b) Additive** — keep the signal write on `CALL`, and give `SRC` a new signal-free `"heard"`
  upsert carrying only `last_seen` and `gw`.

**We chose (b).** It loses nothing and separates the two claims honestly: RSSI/SNR belong to `CALL`
because that is what we measured; identity and gateway status belong to `SRC` because that is what
the beacon asserts. `hw_id`/`lora_mod`/`mesh` are excluded from the originator's row for the same
reason — they describe the heard transmission.

The cost, stated plainly: MHeard and UDP now follow different attribution rules. That is exactly the
shape of divergence that produced the v22 bug, so it is a documented, tested invariant rather than
an accident — see `storage/mheard_attribution_tests.py`, whose first case asserts _both_ halves.
Extending the same treatment to the UDP path is a reasonable follow-up and deliberately out of scope
here.

`GW` needed no migration: `station_positions.gw` already exists and `query.py:298` already surfaces
it. `LATEST_SCHEMA_VERSION` stays at 25.

### The placement trap, for the third time

The `"heard"` upsert must run **before** `_store_mheard`'s early return. `_store_mheard` returns
True on a throttle hit and `store_message` returns on that same line, so code one branch later is
silently skipped for every throttled MHeard frame — under real traffic, most of them.

This is the third instance of this exact shape in this repo (link-check ingest, gateway-uptime
recorder, now this). The regression test forces the throttle and was verified by mutation: moving
the call after the return turns it red.

### Decision 2 — `PP` is parsed and exposed, not persisted

`PP` is the HEY beacon's per-hop link chain, and it is the only way to see a weak link two hops out.
We parse it (`src/mcapp/hey_path.py`) and pass it through for the live view. We do **not** store it.

Two reasons, both structural rather than effort-based:

1. **It carries no callsigns.** The chain is an ordered list of `(ncnt, rssi, snr)` with nothing
   identifying which station each hop was, and `PL` is only a count. A consumer can say at which
   _position_ a link was weak, never _which station_.
2. **It self-censors at exactly the interesting depth.** The firmware's new fail-soft drops `PP`
   (then `DIST`) once the register JSON would exceed 244 chars. Counted against the real builder:

   | relay hops | MH JSON | `PP`        |
   | ---------- | ------- | ----------- |
   | 0–4        | 193–237 | present     |
   | 5          | 248     | **dropped** |
   | 6–7        | 259–270 | **dropped** |

A schema migration for an anonymous series that disappears on deep paths buys nothing anyone can
act on. Revisit if hop identities ever reach the wire.

### Parser invariants

Five firmware behaviours a naive parser gets wrong, each cited to firmware `file:line` in
`hey_path.py`'s module docstring. The load-bearing one:

> **RSSI is a positive magnitude on the wire.** `appendHeySignalReport()` emits
> `String(rssi*-1.0, 0)`, so `-101 dBm` arrives as `101`.

A parser that trusts the sign inverts every reading in a way that still looks physically plausible —
which is to say, unnoticeably. Legacy-shape detection is by **comma count** in the leading token,
mirroring the firmware: 0 and 2 commas valid, 1 comma rejected. We do not invent a rule the firmware
does not have.

## 3. `FWDATE` on the webapp

Backend needed nothing: `transform_ble` already passes the whole `I` register through to the SSE
`ble:status` event. The webapp types it as a **number** (`FLASH_VERSION`, `YYYYMMDD`) and formats it
with pure string arithmetic — deliberately never through `Date`/`toLocaleDateString`, because a
build stamp has no timezone and constructing a `Date` can shift the displayed calendar day. The spec
asserts the exact output string so a future refactor back to `Date` fails loudly.

Shipped in webapp `1936826`.

---

## 4. What we did not do

- **No `GCB` array change.** It is the durable fix for the `I` overflow (saves ~34 chars) but it is
  an app-visible contract change; upstream is coordinating it separately. Our salvage covers the gap.
- **No `blelen + 2` `uint8_t` fix on our side** — it is a firmware bug and now unreachable:
  `mheard_functions.cpp:385` is the only `'D'`-frame caller of `addBLEOutBuffer`, and the fail-soft
  caps it at 244.
- **No handling for the `--mheard` table-dump schema divergence.** It carries none of the three new
  fields, but MCProxy never sends `--mheard`. All three are treated as optional anyway, which costs
  nothing.
- **No UDP-path attribution change.** See Decision 1.
